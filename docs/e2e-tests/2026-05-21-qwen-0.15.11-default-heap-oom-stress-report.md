# Qwen Code 0.15.11 Default-Heap OOM Stress Report

Date: 2026-05-21

## Test Scope

This report records a round of default-heap stress testing against the latest local build of Qwen Code `0.15.11`.
The goal of this round is to verify: without artificially lowering the memory limit, can the current code still reproduce
the long-session OOM mentioned in the issues, and is there any new risk under more extreme large-output scenarios.

This round covers three models:

- `pai/glm-5`
- `qwen3.6-plus`
- `DeepSeek/deepseek-v4-pro`

The test is split into two parts:

1. Realistic long-task, multi-agent concurrent review loop.
2. Amplified foreground stdout stress, i.e., using large-scale foreground shell stdout to amplify
   tool-output path pressure.

## Key Conclusions

The latest local build performs noticeably better on the "long-session V8 heap OOM" path that the issues care about most.
Based on this round of default-heap, multi-model, multi-agent, long-task stress testing, we can consider that this PR has
essentially resolved the previously encountered long-session heap OOM problem, at least in the sense that the original heap OOM
can no longer be reproduced along the current reproduction dimension.

The realistic long-task, multi-agent concurrent test executed a total of:

- 23 worker turns
- about `719,094,118` reported total tokens
- 77 agent tool calls
- 856 total tool calls

This part did not reproduce any traditional V8 heap OOM signatures:

- `JavaScript heap out of memory`
- `Reached heap limit`
- `Ineffective mark-compacts near heap limit`
- `Allocation failed`

The highest process-tree RSS during the realistic long-task phase was `874.7 MiB`, and the highest root-process RSS was
`219.1 MiB`. This shows that under the default heap, the current code does not easily reproduce the kind of long-task
heap OOM crash from the original issue.

The second phase, amplified stdout stress, is more aggressive. It executed a total of 18 payload attempts,
covering three models and foreground stdout payloads from `128 MiB` to `2048 MiB`.

The results are:

- All three models successfully ran through the `1536 MiB` payload.
- The highest successful process-tree RSS was `5964.7 MiB`, occurring with `qwen3.6-plus`
  on the `1536 MiB` payload.
- At the `2048 MiB` payload, a new extreme large-output failure appeared.

The `2048 MiB` results:

- `pai/glm-5`: `exit=1`, empty stdout, no standard OOM text.
- `qwen3.6-plus`: `exit=1`, empty stdout, no standard OOM text.
- `DeepSeek/deepseek-v4-pro`: a V8 fatal appeared:
  `Check failed: i::kMaxInt >= len`, with the stack in
  `v8::String::NewFromOneByte` / `node::StringBytes::Encode` /
  `DecodeUTF8`.

This new problem is not the traditional long-session heap OOM from the original issue. It looks more like a
V8 string-length limit or large-output handling problem triggered when multi-GiB foreground stdout is decoded/constructed
into a JS string. We recommend tracking it as a large-output follow-up, rather than treating it as a failure of
the current long-session heap-pressure fix.

## Phase 1: Realistic Long-Task, Multi-Agent Concurrent Stress

### Test Form

Each model worker reuses the same session and keeps `--resume`-ing. Each round asks Qwen Code to:

- Perform read-only code review and code search;
- Concurrently launch at least 4 `agent` tool calls in the same round;
- Focus on memory-related areas such as chat history, compaction, subagent runtime, non-interactive
  streaming, and provider adapters;
- Keep a sufficiently detailed final answer so that the session history grows naturally.

The runner samples process-tree RSS every second, with no additional heap cap set.

This part was actively stopped with `SIGTERM` after memory was observed to be relatively stable, in order to switch to the second-phase
amplified stdout stress. So the `SIGTERM` in the table is not an OOM.

### Phase 1 Interpretation

This is the data in this round that best demonstrates that the original long-session OOM has clearly improved.

This set of tests is heavier than the small PR review / code navigation on May 18: it includes more
`--resume`, more subagent activity, larger reported token counts, and more tool calls.
But the process-tree RSS stays below `0.9 GiB` throughout, and no traditional V8 heap OOM appeared.

This cannot prove that all user OOMs can no longer occur, but it at least shows that the current build, under the default heap,
can no longer easily reproduce the kind of long-session heap-pressure OOM from the issues.

## Phase 2: Amplified Foreground Stdout Stress

### Test Form

The second phase deliberately amplifies the shell-output path pressure. For each model and each payload size, the
parent session and concurrent agents are asked to run foreground shell commands that output a large amount of `x` to stdout:

```bash
node -e "const chunk='x'.repeat(1024*1024); for (let i=0; i<N; i++) process.stdout.write(chunk)"
```

Payload sizes:

- `128 MiB`
- `256 MiB`
- `512 MiB`
- `1024 MiB`
- `1536 MiB`
- `2048 MiB`

This is synthetic stress, not a normal code review workload. Its purpose is to verify whether extremely large foreground
stdout still pushes Qwen Code onto a dangerous memory path.

### Why RSS Exceeds the Node Heap Limit

This machine's Node heap limit is about `4144 MiB`, but the process-tree RSS reached up to about
`5964.7 MiB`. This is not contradictory:

- RSS includes the V8 heap, external buffers, native allocations, loaded modules, child processes,
  and memory not counted toward the old-space heap.
- The highest peak in the amplified phase usually occurs in a child Node process, not the root wrapper.
- So root RSS can stay relatively low while process-tree RSS is very high.

## Comparison with Historical Reports

In the May 18 maintainer benchmark, Qwen's process-tree RSS peaked mostly between
`942.5 MiB` and `1006.6 MiB` under ordinary tasks. These data mainly show that, at the time, Qwen Code's
task-time footprint was noticeably higher than Claude Code's.

The May 19 runtime diagnostics report further split out two lines:

- startup/config RSS: often pushed up by the normal config and MCP child processes;
- long-session heap OOM: leans more toward history / compaction / clone pressure.

This round's May 21 data further supports this split:

- realistic long-task, multi-agent, long-session scenarios stay below `0.9 GiB`, without hitting heap
  OOM;
- amplified stdout can push process-tree RSS to `5.96 GiB`, and at `2048 MiB`
  triggers another class of V8 string-length fatal.

Therefore, compared with the traditional long-session heap OOM in the original issue, the current build is clearly more stable. But this does
not mean Qwen Code has no remaining large-output memory risk.

## New Finding: Extreme Foreground Stdout Fatal Path

The new problem found in this round is not the original heap OOM, but a
string/decoding fatal under multi-GiB foreground stdout:

```text
Fatal error in , line 0
Check failed: i::kMaxInt >= len.
...
v8::String::NewFromOneByte
node::StringBytes::Encode
node::encoding_binding::BindingData::DecodeUTF8
```

Trigger conditions:

- Model: `DeepSeek/deepseek-v4-pro`
- Payload: `2048 MiB`
- Peak tree RSS: `4660.4 MiB`
- Largest process RSS: `4527.6 MiB`
- The runner records the exit as `SIGTERM`, because after the fatal output was captured, a remaining child process was still spinning at high CPU
  and was manually terminated.

`pai/glm-5` and `qwen3.6-plus` also failed at `2048 MiB`, presenting as empty stdout and
exit code `1`, but stderr did not capture a V8 fatal stack.

### Severity

This is a real robustness problem, but the trigger condition is multi-GiB foreground stdout,
not a normal code review task. It also does not prove that the current long-session heap-pressure fix has failed.

### Was It Introduced by This PR?

This round has no evidence that the `2048 MiB` stdout failure is a regression introduced by the current memory PR.

Reasons:

- The failure path is foreground shell stdout decode / string construction.
- The original issue path is long-session history, compaction, and clone pressure.
- This round did not run a pre-PR baseline with the same payload, so it cannot be attributed as a regression.
- The failure only appears at the deliberately extreme `2048 MiB` payload; `128 MiB` to
  `1536 MiB` all complete.

We recommend treating it as a dedicated large-output follow-up: stream / spool / hard-cap
foreground shell output earlier, avoiding constructing a multi-GiB JS string in memory. Unless the current PR's goal
explicitly includes "any multi-GiB foreground stdout must be handleable," we do not recommend treating it as a
blocker for the current PR.

## Conclusion

1. The latest local `0.15.11` build is clearly better in the direction of the long-session heap OOM reported in the issues.
   Based on the current default-heap stress test results, we can consider that this PR has essentially resolved the
   previously encountered long-session heap OOM reproduction path.

2. Under the default Node heap, the realistic long-task + multi-agent review loop did not reproduce a traditional
   V8 heap OOM on any of the three models `pai/glm-5`, `qwen3.6-plus`, or `DeepSeek/deepseek-v4-pro`.

3. The synthetic foreground stdout stress can still push process-tree RSS very high. The current build held up through the
   `1536 MiB` payload on all three models, with a highest successful tree RSS of `5964.7 MiB`.

4. An independent extreme large-output problem remains: around the `2048 MiB` stdout payload, Qwen Code
   may fail before outputting the JSON result; the DeepSeek case captured a V8 string-length fatal.

5. This new finding is important, but it looks more like a follow-up large-output robustness problem and should not be treated directly as a
   blocker for the long-session heap-pressure mitigation.
